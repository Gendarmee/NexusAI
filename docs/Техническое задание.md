# ТЕХНИЧЕСКОЕ ЗАДАНИЕ

## Проект: Агрегатор нейросетей (AI Gateway)

---

## 1. ОБЩИЕ СВЕДЕНИЯ

### 1.1. Наименование проекта
Агрегатор нейросетей с системой подписок и биллингом токенов.

### 1.2. Назначение проекта
Создание платформы, предоставляющей пользователям единый доступ к различным языковым моделям (LLM) через проксирование API OpenRouter, с системой подписок, биллингом токенов и полным observability стеком.

### 1.3. Цели проекта
- Предоставить пользователям доступ к множеству LLM через единый интерфейс
- Реализовать систему монетизации через подписки и токены
- Обеспечить полную наблюдаемость системы (логи, метрики, трейсинг)
- Построить масштабируемую микросервисную архитектуру

---

## 2. ФУНКЦИОНАЛЬНЫЕ ТРЕБОВАНИЯ

### 2.1. Пользовательский сервис (User Service)

#### ФТ-1.1. Регистрация и аутентификация
- Система должна предоставлять API для регистрации пользователей по email и паролю
- Система должна предоставлять API для аутентификации и выдачи JWT-токенов
- Система должна поддерживать refresh token механизм
- Система должна валидировать email и обеспечивать безопасность паролей (хеширование)

#### ФТ-1.2. Управление профилем
- Система должна предоставлять API для получения информации о профиле пользователя
- Система должна предоставлять API для обновления данных профиля
- Система должна предоставлять API для смены пароля

#### ФТ-1.3. Авторизация
- Система должна проверять валидность JWT-токенов при каждом защищённом запросе
- Система должна поддерживать роли пользователей (user, admin)

### 2.2. Сервис подписок и баланса (Billing Service)

#### ФТ-2.1. Управление тарифами
- Система должна хранить каталог доступных тарифов (название, цена, количество токенов, срок действия)
- Система должна предоставлять API для получения списка тарифов
- Система должна позволять администраторам создавать и редактировать тарифы

#### ФТ-2.2. Управление подписками
- Система должна создавать подписку для пользователя после успешной оплаты
- Система должна активировать подписку и устанавливать срок действия
- Система должна отслеживать статус подписки (активна, истекла, отменена)
- Система должна предоставлять API для получения информации о текущей подписке пользователя

#### ФТ-2.3. Биллинг токенов
- Система должна вести учёт баланса токенов для каждого пользователя
- Система должна начислять токены при активации подписки
- Система должна списывать токены при использовании LLM
- Система должна блокировать запросы к LLM при нулевом или отрицательном балансе
- Система должна предоставлять API для получения текущего баланса токенов
- Система должна предоставлять API для получения истории транзакций (начисления и списания)

#### ФТ-2.4. Обработка событий
- Система должна подписываться на события об успешной оплате из брокера сообщений
- Система должна публиковать события об изменении баланса токенов

### 2.3. Сервис платежей (Payment Service)

#### ФТ-3.1. Создание платежей
- Система должна предоставлять API для создания платежа за подписку
- Система должна интегрироваться с внешним платежным шлюзом (Stripe/YooKassa/CloudPayments)
- Система должна возвращать пользователю ссылку на страницу оплаты или данные для оплаты

#### ФТ-3.2. Обработка вебхуков
- Система должна принимать вебхуки от платежной системы об успешной оплате
- Система должна принимать вебхуки о неуспешной оплате
- Система должна обеспечивать идемпотентность обработки вебхуков (защита от повторной обработки)
- Система должна верифицировать подпись вебхуков для безопасности

#### ФТ-3.3. Публикация событий
- Система должна публиковать событие `PaymentSucceeded` в брокер сообщений при успешной оплате
- Система должна публиковать событие `PaymentFailed` при неуспешной оплате
- Система должна включать в событие данные о пользователе, тарифе и сумме платежа

### 2.4. Сервис чатов и проксирования (Chat Service)

#### ФТ-4.1. Каталог моделей
- Система должна синхронизировать с OpenRouter список доступных моделей
- Система должна помечать модели, доступные по бесплатному тарифу
- Система должна предоставлять API для получения списка доступных моделей
- Система должна отображать стоимость токенов для каждой модели

#### ФТ-4.2. Проксирование запросов
- Система должна принимать запросы от пользователей (промпт, выбранная модель, параметры)
- Система должна форматировать запросы согласно API OpenRouter
- Система должна отправляать запросы в OpenRouter от имени системы
- Система должна возвращать ответы от OpenRouter пользователю

#### ФТ-4.3. Стриминг ответов
- Система должна поддерживать Server-Sent Events (SSE) для потоковой выдачи ответов
- Система должна передавать токены от OpenRouter пользователю в реальном времени
- Система должна корректно обрабатывать обрывы соединения

#### ФТ-4.4. Учёт токенов
- Система должна получать от OpenRouter информацию о потраченных токенах (`prompt_tokens`, `completion_tokens`)
- Система должна отправлять команду на списание токенов в Billing Service
- Система должна сохранять информацию о каждом запросе (модель, количество токенов, время)

#### ФТ-4.5. Управление лимитами
- Система должна отслеживать использование бесплатных моделей OpenRouter
- Система должна применять rate limiting для бесплатных моделей (не превышать лимиты OpenRouter)
- Система должна автоматически переключаться на платные модели при достижении лимитов (если у пользователя есть баланс)
- Система должна возвращать понятные ошибки при превышении лимитов

#### ФТ-4.6. История диалогов
- Система должна сохранять историю переписки для каждого диалога
- Система должна предоставлять API для создания нового диалога
- Система должна предоставлять API для получения истории диалога
- Система должна передавать контекст (историю) в OpenRouter для каждого запроса

## 3. НЕФУНКЦИОНАЛЬНЫЕ ТРЕБОВАНИЯ

### 3.1. Производительность и масштабируемость

#### НФТ-1.1. Время отклика
- Время до получения первого токена (Time to First Byte) не должно превышать время ответа OpenRouter + 200 мс на обработку бэкендом
- API endpoints должны отвечать в течение 100 мс (без учёта внешних вызовов)

#### НФТ-1.2. Параллельные соединения
- Chat Service должен поддерживать тысячи одновременных SSE-соединений
- Все сервисы должны использовать асинхронную обработку запросов

#### НФТ-1.3. Горизонтальное масштабирование
- Все сервисы должны быть stateless (без состояния)
- Архитектура должна позволять масштабировать сервисы независимо добавлением новых инстансов

### 3.2. Надёжность и отказоустойчивость

#### НФТ-2.1. Обработка ошибок внешних API
- При получении ошибки 429 (Too Many Requests) от OpenRouter система должна применять экспоненциальную задержку (Exponential Backoff)
- При недоступности OpenRouter система должна возвращать пользователю понятную ошибку, а не зависать по таймауту
- Система должна реализовывать Circuit Breaker паттерн для внешних вызовов

#### НФТ-2.2. Согласованность данных
- Списание токенов и сохранение сообщения в историю должно быть согласованным
- При сбое во время стриминга сообщение должно сохраняться с пометкой о неполном ответе
- Обработка платежей должна быть идемпотентной

#### НФТ-2.3. Восстановление после сбоев
- Система должна корректно обрабатывать перезапуски сервисов
- Брокер сообщений должен гарантировать доставку событий (at-least-once)

### 3.3. Безопасность

#### НФТ-3.1. Хранение секретов
- API-ключи OpenRouter и другие секреты должны храниться в зашифрованном виде
- Секреты не должны храниться в коде или в открытом виде в базе данных
- Должны использоваться переменные окружения или специализированные хранилища секретов

#### НФТ-3.2. Защита от злоупотреблений
- Система должна применять rate limiting на уровне API для каждого пользователя
- Лимиты должны предотвращать исчерпание бесплатных квот OpenRouter одним пользователем
- Система должна валидировать все входные данные для предотвращения инъекций

#### НФТ-3.3. Конфиденциальность данных
- В логах запрещается записывать полные тексты промптов пользователей
- Логи должны содержать только идентификаторы, статусы и метаданные
- Система должна соответствовать требованиям по защите персональных данных

### 3.4. Наблюдаемость (Observability)

#### НФТ-4.1. Единый коллектор (Grafana Alloy)
- Все телеметрия-данные (логи, метрики, трейсы) должны собираться единым агентом Grafana Alloy
- Конфигурация Alloy должна храниться в репозитории (Infrastructure as Code)

#### НФТ-4.2. Метрики (Prometheus)
- Каждый сервис должен экспонировать метрики в формате Prometheus
- Обязательные метрики:
    - Количество HTTP-запросов с лейблами (method, status, service)
    - Гистограмма задержек HTTP-запросов
    - Количество запросов к OpenRouter по моделям
    - Количество потраченных токенов (prompt/completion)
    - Текущий баланс токенов пользователей
- Prometheus должен скрейпить метрики каждые 15 секунд

#### НФТ-4.3. Трейсинг (Tempo)
- Все сервисы должны генерировать распределённые трейсы через OpenTelemetry SDK
- Трейсы должны отправляться по протоколу OTLP gRPC на Grafana Alloy
- Каждый HTTP-запрос между сервисами должен пробрасывать заголовки W3C Trace Context (`traceparent`)
- Sampling rate для учебного проекта: 100% (все запросы трассируются)

#### НФТ-4.4. Логирование (Loki)
- Все сервисы должны писать логи в структурированном JSON-формате в stdout
- Каждая лог-запись должна содержать поля: `trace_id`, `span_id`, `service_name`, `correlation_id`
- Alloy должен собирать логи из Docker-контейнеров и отправлять в Loki
- В Grafana должна работать корреляция логов и трейсов (переход от лога к трейсу по `trace_id`)

#### НФТ-4.5. Визуализация (Grafana)
- Должны быть настроены Data Sources: Prometheus, Tempo, Loki, PostgreSQL
- Минимум 3 дашборда:
    - **System Overview**: RPS, Latency (p50/p95/p99), Error Rate по каждому сервису
    - **LLM Proxy Dashboard**: запросы к OpenRouter, токены, статусы, время ответа по моделям
    - **Billing Dashboard**: активные подписки, баланс токенов, платежи
- Должны быть настроены Alert Rules (например, алерт при Error Rate > 5% за 5 минут)

### 3.5. CI/CD и управление артефактами

#### НФТ-5.1. Nexus Repository Manager
- Nexus должен быть развёрнут как приватный репозиторий артефактов
- Nexus должен хранить JAR-файлы для Java-сервисов (Maven repository)
- Nexus должен хранить NuGet-пакеты для C#-сервисов
- Nexus должен хранить Docker-образы всех микросервисов
- Общие библиотеки (SharedKernel, Contracts) должны паблишиться в Nexus при мерже в main

#### НФТ-5.2. CI Pipeline
При пуше в main CI должен:
- Определить изменённые сервисы в монорепозитории
- Собрать изменённые сервисы
- Прогнать unit-тесты
- Запушить артефакты в Nexus (JAR / NuGet / Docker image)
- Задеплоить обновлённые сервисы

#### НФТ-5.3. Монорепозиторий
- Проект должен использовать монорепозиторий (один Git-репозиторий для всех сервисов)
- Структура должна разделять сервисы, общие библиотеки и инфраструктуру
- CI/CD должен билдить только изменённые сервисы, а не весь монорепозиторий

### 3.6. Документация API

#### НФТ-6.1. Swagger/OpenAPI
- Каждый сервис должен автоматически генерировать OpenAPI (Swagger) документацию
- Документация должна быть доступна по URL `/swagger` или `/swagger-ui.html`
- Все endpoints должны иметь описания (summary, description)
- Все request/response модели должны иметь описания полей
- Документация должна позволять тестировать API прямо из браузера (Try it out)

## 4. ТРЕБОВАНИЯ К АРХИТЕКТУРЕ

### 4.1. Микросервисная архитектура
- Система должна состоять из 4 независимых микросервисов: User, Billing, Payment, Chat
- Сервисы должны общаться через REST API (синхронно) и брокер сообщений (асинхронно)
- Каждый сервис должен иметь свою базу данных (или схему в общей БД)

### 4.2. Брокер сообщений
- Система должна использовать RabbitMQ для асинхронной коммуникации
- События должны быть идемпотентными
- Брокер должен гарантировать доставку сообщений (at-least-once)

### 4.3. База данных
- Система должна использовать PostgreSQL
- Каждый сервис должен использовать свою схему (schema) в базе данных
- Должны использоваться миграции для управления схемой БД

## 5. ТРЕБОВАНИЯ К ТЕХНОЛОГИЧЕСКОМУ СТЕКУ

### 5.1. Бэкенд
- Java 17+ с Spring Boot (для части сервисов)
- C# .NET 8+ (для части сервисов)
- Выбор стека для каждого сервиса определяется командой

### 5.2. Инфраструктура
- Docker и Docker Compose для локальной разработки и деплоя
- PostgreSQL 16+
- RabbitMQ 3.x
- Nexus Repository Manager 3.x

### 5.3. Observability стек
- Grafana Alloy (коллектор)
- Prometheus (метрики)
- Grafana Tempo (трейсы)
- Grafana Loki (логи)
- Grafana (визуализация)

### 5.4. CI/CD
- GitHub Actions или GitLab CI
- Conventional Commits для форматирования коммитов

---

## 6. ТРЕБОВАНИЯ К ТЕСТИРОВАНИЮ

### 6.1. Unit-тесты
- Каждый сервис должен иметь unit-тесты для бизнес-логики
- Покрытие кода тестами: минимум 70%

### 6.2. Интеграционные тесты
- Должны быть интеграционные тесты для проверки взаимодействия сервисов
- Тесты должны проверять корректность обработки событий в брокере сообщений

### 6.3. API-тесты
- Должны быть тесты для проверки API endpoints
- Тесты должны проверять валидацию входных данных и коды ответов

---

## 7. ТРЕБОВАНИЯ К РАЗВЁРТЫВАНИЮ

### 7.1. Локальная разработка
- Система должна подниматься одной командой `docker-compose up`
- Все зависимости (БД, брокер, observability стек) должны быть в `docker-compose.yml`

### 7.2. Продакшен
- Система должна быть готова к развертыванию в Kubernetes или Docker Swarm
- Конфигурация должна управляться через переменные окружения
